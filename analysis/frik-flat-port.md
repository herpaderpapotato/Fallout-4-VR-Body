# FRIK on flat Fallout 4 1.11.240 (FRIK-flat): inventory, design, plan

Status: living document (2026-11-14). Progress and resume prompt: `work/handoff/frik-integration.md`.

FRIK (`mods/Fallout-4-VR-Body`, 21b585c1) and the F4VR-CommonFramework parts it builds with (`mods/F4VR-CommonFramework`,
5677388) are **compiled as they are** against the flat CommonLibF4 (`extern/commonlibf4`, 1.11.240), with:

- a compatibility layer (`frik-flat/vrshim/`): the CommonLibF4VR API surface FRIK expects, VR addresses bridged to flat
  ones, the VR player nodes, an OpenVR `IVRSystem` backed by fo4flatvr;
- `#ifdef FRIK_FLAT` edits at the call sites where behaviour has to differ (grep `FRIK_FLAT` / `FRIK-flat C<n>`);
- an export API in fo4flatvr (`plugin/src/plugin/FrikBridge*`) that feeds it.

`mods/` is never edited; `frik-flat/frik-src` and `frik-flat/fw-src` are copies.

## 1. Inventory of engine symbols

Generated by `frik-flat/tools/port_inventory.py` from `analysis/db/frik_flat_symbols.csv` (extraction:
`analysis/tools/frik_flat_inventory.py`: VR RVA -> 1.10.163 name via VR address-library ids / PDB names -> 1.11.240 via
`func_matches.csv`, shared ids and data anchors; call and patch sites re-found inside the mapped flat function).
At run time `vrshim::flatAddress` serves the table (`frik-flat/generated/FrikFlatAddresses.inl`, from `tools/gen.py`).

What does *not* need an address: every struct layout and virtual slot FRIK touches comes from the flat CommonLibF4's
headers, so recompiling fixes them (NiNode 0x140 vs VR 0x180, BSFlattenedBoneTree, PlayerCharacter members, ...). The
VR-only members (`PlayerCharacter::vrNodes`, VR settings) fail to compile and are handled in section 2.

### 2.1 The VR player nodes from xrcore poses (`vrshim/src/Bridge.cpp`)

Each game frame, at the frame hook, before FRIK's update (`vrshim::bridge::frameUpdate`):

- `HMDNode.world` = `PlayerCamera::cameraRoot.world` - the camera fo4flatvr builds from the head pose.
- `RoomNode.world` = heading only: yaw(camera) - yaw(head in the OpenXR reference space); origin such that the HMD's
  room-relative XY is its reference-space XY, and **z = the player's feet**. So `HMDNode/UprightHmdNode.local.z` = eye
  height above the feet, which FRIK's body pitch / height logic reads (`Skeleton::getBodyPitch`).
- `UprightHmdNode` = HMD with yaw only. `PlayerWorldNode` = identity parent of the room.
- `Primary/SecondaryWandNode.world` = camera . grip-in-head (metres x fUnitsPerMeter) . **C**, C = fo4flatvr's
  `[Hands] fGripRotX/Y/ZDeg`, `fGripOffsetX/Y/Z` (default rot X -60 deg): the same OpenXR-grip -> FO4VR-wand frame
  fo4flatvr's hands code uses with FRIK's weapon JSONs. Left hand: mirrored C. Children keep their FO4VR binds
  (`PrimaryWeaponToWandNode` (0,-4,1) etc.) and are propagated.
- `weaponLeftNode` = the flat 1st-person skeleton's `WeaponLeft`.

The head-relative grip comes from the same Present-time snapshot as fo4flatvr's own hands (relative to the head pose
handed to the camera for the next game frame), so FRIK's hands have the same latency/registration fo4flatvr's verified
hands had. Math in fo4flatvr Hands' column-vector convention (`vrshim/XfMath.h`).

### 2.2 Smooth movement (C17, bridge v3)

**What FO4VR does** (Ghidra, read-only): `Main::OnIdle` VR D83EB2..D83EC4 = `mov rbx,[g_vrWorldData 59429C0]; call 1BA7A80;
mov rcx,rbx; call 1BA7BA0`. 1BA7BA0 copies the OpenVR HMD pose (1BAB570) into `g_vrWorldData+0x180..0x1AC`; it is VR-only
(no flat function, `g_vrWorldData` unresolved). FRIK wraps that call (`GameHooks.cpp hookSmoothMovement`): once per frame,
before the VR engine reads the HMD, `SmoothMovementVR::onFrameUpdate` sets `PlayerWorldNode.local.translate =
smoothed(player pos) - player pos (+ FRIK's HMD height offset in z)`. The HMD camera hangs under PlayerWorldNode, so the
camera gets the smoothed position. Helpers: `f4vr::IsInAir` VR DC3230 = flat C5BDB0 `Actor::IsJumping` (same body:
hknpCharacterContext state 2/1, or 6 with vfunc +0x2D0 false); `isInInternalCell` = parentCell->IsInterior (no address).

**Flat**: no PlayerWorldNode under the camera - fo4flatvr's FirstPersonState hooks (GameBridge.cpp, head authority) build the
camera as `data.location + GetTranslation()`. Choice: **through the bridge, not a FRIK-side hook.** A FRIK hook on the
camera would fight fo4flatvr's own FirstPersonState vtable hooks (and the stereo agent's FOV code there), and an offset
computed at FRIK's frame (C351F3, after the camera) would be applied one frame late against the next frame's capsule
position, which re-adds exactly the per-frame step it is meant to remove. So:
- fo4flatvr `HkFpUpdate` calls `frikbridge::StepCameraOffset()` before the game's update (player position final for the
  frame) -> FRIK.dll's registered callback -> `FRIK::smoothMovementFlat` -> FRIK's unchanged `SmoothMovementVR::onFrameUpdate`
  (config from FRIK_Config/FRIK.toml) -> offset `newPos - curPos` (C17 getter; without the HMD height offset, which on flat
  the camera's own eye height already covers).
- `HkFpGetPos` adds the offset to the head-authority (and the legacy) translation; the rig-fit call (D7C9CD) keeps the raw value.
- FRIK.dll in **smooth-movement-only mode** (`[FRIK] bBody=0`, default until the body is visible): logger + F4SE init + config,
  the camera callback, nothing else (no hooks/patches/skeleton/frame). fo4flatvr refuses `SetFrikActive(1)` and the frame
  callback while bBody=0, so the floating gun, hidden arms, controller models and per-hand activation are unchanged.
- Resets: FRIK's own (teleport > 2000 u, not-moving drift > 10 u); C17 adds: no camera update for > 0.5 s (loading screen,
  third person) -> reseed; player without parentCell/3D -> no offset.
- Switches: `[FRIK] bSmoothMovement` (default 1), `bSmoothHorizontal` (default 0 = height only), FRIK.toml
  `[SmoothMovementVR]` knobs; pipe `frik [smooth on|off|smooth xy on|off|reset]`.
- Measured 15 Nov 00:17 (SteamVR+vremu, vrtest_sanctuary, deployed files, frik-flat/tools/smooth_session.py, work/frik-flat/
  smooth-20261115-001649): FRIK.dll smooth-only mode loads (`frik`: body=0 framecb=0 active=0), gun not stepped aside (aside=0,
  armsHidden=1), clean exit. 6 s run over uneven ground (~2230 u): camera z high-pass (0.25 s) RMS 0.834 -> 0.144 u, max
  per-frame step 3.41 -> 0.37 u, 2nd-difference RMS 0.504 -> 0.016 (capsule 0.835 / 0.772 in both runs). Horizontal (FRIK
  default): camera 39-51 u behind the capsule while running; vremu 20 cm (14 u) head step -> camera error up to 10 u, 1.6-3.5 u
  after 3 s (0.001 without smoothing): roomscale moves the capsule after the head and x/y smoothing lags that move. HIGH impact
  for comfort -> `[FRIK] bSmoothHorizontal=0` (default, plugin side: x/y of the offset dropped) = height only; built 00:20, not

## 3. OpenVR usage and replacement

Real OpenVR calls (not types) in FRIK + framework: `IVRSystem` in `vrcf/VRControllersManager` (state with pose, device
index by role, poses), `VRControllersHaptic` (TriggerHapticPulse), `VRControllersSuppressor` (vtable slots 34/35),
`perf/FrameSampler` (compositor timing), `render/SubmitHook` (IVRCompositor::Submit vtable hook for overlays),
`imgui/ImGuiKeyboard` (IVROverlay keyboard). FRIK itself reads input only through `vrcf::VRControllers` and types.

**First build (done):** FRIK.dll defines the `openvr_api` entry points itself (`vrshim/src/OpenVRShim.cpp`, built with
`VR_API_EXPORT`, no openvr_api.dll import). `VR_GetGenericInterface("IVRSystem_019")` returns `FlatVRSystem`, an
`vr::IVRSystem` backed by fo4flatvr's snapshot (`FO4FLATVR_GetFrikBridge()->GetFrame`): devices 0 HMD / 1 left / 2 right,
poses = OpenXR grip poses in the reference space (= OpenVR tracking convention), buttons mapped as SteamVR's legacy
Oculus Touch binding (A/X -> `k_EButton_A`, B/Y -> `ApplicationMenu`, grip >= 0.7 -> `Grip`, trigger >= 0.9 ->
`SteamVR_Trigger`, stick click -> `SteamVR_Touchpad`; axes [0] stick, [1] trigger, [2] grip). The framework's whole input
layer (`VRControllersManager` bindings, press/hold/tap/double, axis repeat, haptic patterns, suppressor) runs unchanged.
Compositor/overlay/chaperone return null - the framework treats that as "no runtime": overlays drawn through the VR
submit hook, the VR keyboard and compositor timing are off.

Gaps: no capacitive touch states (fo4flatvr's `xr::ControllerState` has none; touch = pressed / trigger > 0.05 / stick
deflection); haptics are counted, not played (the bridge has no path to `xr::Runtime::Vibrate` without a Presenter edit);
FRIK's button presses also reach the game through fo4flatvr's virtual pad (no input suppression between them yet).

**Later (for ROCK):** the same `FlatVRSystem` exported from a standalone `openvr_api.dll` placed next to ROCK (ROCK
imports openvr_api.dll directly and needs `IVRSystem` + compositor poses; ROCK-compat.md). The shim is already written
against the real OpenVR ABI, so it moves into its own DLL with a small loader for the bridge.

## 4. Address bridging at run time

`vrshim::FlatOffset(0xVR)` / `FlatId(n)` replace `REL::Offset` / `REL::ID` in the copies; `F4SE-VR`-style
`DEFINE_MEMBER_FN` uses `vrshim::flatAddress`. Every lookup is registered; `F4SEPlugin_Load` logs
**`FRIK-flat initialised, N/M addresses resolved (L low-confidence)`** plus one line per unresolved address.

Unresolved addresses never come back as 0: code -> a `xor eax,eax; xorps xmm0,xmm0; ret` stub, data -> a zeroed 64 KiB
block, both outside the game image, so every hook/patch helper (`verifyCallSite`, `verifyPatchBytes`, the main-loop
hook) still refuses them by `inGameImage`. All patches/hooks are byte-checked before writing.

## 6. fo4flatvr <-> FRIK.dll interface and startup order

C ABI in `plugin/src/plugin/FrikBridgeApi.h` (v1): `FO4FLATVR_GetFrikBridge(version)` -> `{GetFrame, Vibrate,
SetFrikActive, IniPath}`; `FO4FlatVR_Frame` = head pose, per hand grip/aim poses (reference space), grip relative to the
head in the camera basis, buttons/axes, left-handed, units per metre, sequence/age.

Startup:
1. F4SE loads both DLLs, then calls `F4SEPlugin_Load` in plugin order (fo4flatvr first by name, but nothing depends on it).
2. FRIK.dll `F4SEPlugin_Load`: `GetModuleHandle("fo4flatvr.dll")` -> `FO4FLATVR_GetFrikBridge(1)`. **Null (fo4flatvr
   absent, `[FRIK] bEnable=0`, version mismatch) -> FRIK-flat stays dormant**: no log, no patch, no hook.
3. Otherwise the framework's load runs (logger, config, `patchAll`, `hookMain`, frame hook), then FRIK-flat logs the
   address line and calls `SetFrikActive(1)`: fo4flatvr switches its own hands code off (`hands::Command("off")`;
   fo4flatvr's `frikbridge::Install` re-applies it if FRIK was first). Hands' W1 hook stays installed and chained.
4. Per XR frame (Presenter thread): `hands::PublishXr` -> `frikbridge::PublishXr` stores the snapshot.
5. Per game frame (main thread, C351F3): FRIK-flat's hook -> `bridge::frameUpdate` (VR nodes) -> FRIK `onFrameUpdate`
   -> previous call target (fo4flatvr Hands W1, a no-op while off) -> `PlayerUpdateEvent` Notify.

Switch: `fo4flatvr.ini [FRIK] bEnable` (default 1, as every feature); FRIK.dll is only deployed for FRIK-flat tests.

**Who owns the per-frame call:** FRIK-flat, at C351F3 (VR: OnIdle +0x27E early in the frame, before the VR engine's
own per-frame arm placement). On flat this is the first main-thread point after animation, scene graph and camera
(analysis/vr-hands-weapon.md 1.3) and the one fo4flatvr's hands verified. It does not run while the game is paused
(Pip-Boy menu): open item for FRIK's Pip-Boy interaction (a second, pause-time call from `Main::OnIdle` C33E62 or
C346AC).
